## 1. Working rules (every session)

- Start with `pwsh -NoProfile -File .\tools\dev.ps1 context`. Read `AGENTS.md` plus the nested
  `src/AGENTS.md` and `tests/AGENTS.md`. Use `dev.ps1 find` and `rg` for focused reads; read only
  the spec sections listed for your session.
- The spec is normative; this plan gives order and scope. If they disagree, follow the spec,
  stop, and tell the user. Never change an acceptance ID.
- The gate is `pwsh -NoProfile -File .\tools\dev.ps1 verify` (exit 0 pass, 1 fail, 2 incomplete).
  Done means exit 0, `"Status":"pass"`, no warnings. Never report a result you did not observe.
- **Ask the user first** before `dotnet restore`, any package change, any install, or any other
  network access.
- No ADO access, no network in tests (fake `HttpMessageHandler`, loopback `FakeAdoServer`). Fixture
  hosts use `.test`. Tests never open files with the default handler.
- Git lifecycle belongs to the developer: inspection commands only; never create a repository,
  commit, or push.
- If the agent sandbox blocks a step this plan requires (network after the user authorizes it,
  the NuGet or PowerShell module cache outside the workspace, loopback sockets or temporary files
  during `verify`), request elevated permission for that command. Never weaken tests or the gate
  to fit the sandbox.
- Data boundary (DD-010, DD-022): synthetic fixtures only.
- Names (DD-024): no `bin`, `obj`, `artifacts`, `build`, `dist`, `coverage`, `target`,
  `TestResults`, `secret(s)` directories under `src/`, `tests/`, `docs/`; no file name matching
  `*.log`, `*credentials*`, `*.local.*`, `*.key`, `*.pem`, `*.pfx`, `*.p12`, `.env*`. Committed
  `.json`/`.xml` must parse; inputs above 1 MiB, including the 300-case suite, are generated by
  tests.
- Tag acceptance tests: xUnit `[Trait("Acceptance", "<ID>")]`, Pester `-Tag '<ID>'`.
- All labels, progress text, and messages come from `.resx` in English and French.
- Keep `tools/check.ps1` under about 240 s; large generated fixtures must stay fast. Report the
  `project-check` duration.
- End each session at a green `verify`, update `docs/plans/README.md`, and hand off: verify
  status and exit code, acceptance IDs covered, spec rows updated, authorizations used,
  deviations, open items, and new French strings for review.

## 5. Work steps

### Session 3.1 — Plans, suites, WIQL

1. **Baseline.** `context`, `verify`.
2. **Registry.** Add the four endpoints exactly as in §6.2. Plans and suites use the testplan area
   with pinned preview versions; mark the fixtures [V-04].
3. **Continuation paging (S3-1).** Reuse the Slice 0 strategy; add fixtures for plans, suites, and
   suite test cases across several pages, including a short page and an empty page that still
   carry a token. Order is preserved across pages.
4. **`Get-AdoTestPlan`.** `-Project`, `-Id` (client-side filter over the listing), `-Name` wildcard
   (case-insensitive, accent-sensitive, NFC on both sides, §11.5). Emit `AdoTestPlan` with
   `WebUrl` from §12.2.
5. **`Get-AdoTestSuite`.** `-PlanId` (or pipeline `AdoTestPlan`), `-SuiteId`, `-Recurse`,
   `-Project`, `-Connection`. Fetch all
   pages, build the tree from parent references, and compute `SuitePath`. Emit a suite alone, or
   with `-Recurse` its subtree depth-first in the order returned by the server (provisional suite
   order, [V-04]).
6. **`Invoke-AdoWiql` (§9.2).** `-Query`, `-Project`, `-Top` (1–20,000), `-Hydrate`. POST body
   `{ "query": … }` with `$top` only when `-Top` is given. Flat results only: a link or tree result
   → `NotSupported` error. Without `-Top`, 20,000 or more IDs → error with a narrower-query hint,
   never truncation. With `-Top`, `LimitApplied = Top`. Server limit errors are surfaced with the
   same hint (V-06). `AsOf` is provenance only (Q-05). `-Hydrate` emits `AdoWorkItem` in query
   order through WorkItemsBatch, with fields = returned columns ∪ convenience fields. No offset
   paging and no invented continuation. The WIQL text is never logged (§6.8).
7. **Format views and help** for the three cmdlets in both cultures.
8. **Tests.** S3-1, S3-3, wildcard matching with accents and NFD input, link/tree rejection.
9. **Live script.** Create `tests/Live/Bulk.Live.ps1` (section 8).
10. `verify` → exit 0.

### Session 3.2 — Bulk retrieval, document, progress

1. **Baseline.** `context`, `verify`.
2. **Suite membership.** SuiteTestCaseList for each suite (all pages); case order follows the
   `order` field within a suite. With `-Recurse`, walk suites depth-first and collect memberships
   in traversal order. Resolve plan name and suite path once per plan for `AdoTestSuiteRef`.
3. **Bulk `TestCaseService` path (§14.2).** Collect all distinct test case IDs from every input of
   the invocation. Run root WorkItemsBatch in chunks of 200 and Phase 1 **once** over all roots
   with one cache, then Phase 2 once per distinct case. Emit one `AdoTestCase` per membership, in
   membership order, each with `Suite` set (copies share the expanded steps).
4. **`Get-AdoTestCase` parameter sets.**
   - ById (existing).
   - BySuite: `-PlanId`, `-SuiteId`, `-Recurse`, `-Project` (defaults to the connection's project;
     taken from `TeamProject` for piped suites), pipeline `AdoTestSuite` by value (`Id` →
     `SuiteId`, `PlanId` → `PlanId`).
   - ByWiql: pipeline `AdoWiqlResult` by value; `Ids` consumed in order.
   - ByWorkItem: pipeline `AdoWorkItem` by value.

   Validate `CollectionUri` first in every set. **Binding hazard:** `AdoTestSuite` and
   `AdoWorkItem` both have an `Id` property that could bind to ById by property name. A suite ID
   must never become a test case ID. Design the parameter sets so typed pipeline objects bind to
   their own set, and prove it with Pester tests for each input type.
5. **Progress.** Core emits typed progress events through the pump; the cmdlet writes
   `ProgressRecord`s with localized activity text for enumeration (suites, pages), fetch
   (batches), and expansion (cases), plus a completed record. Throttle to avoid flooding.
6. **Multi-case document (§12.5).**
   - Cover header: server, collection, project, source (plan and suite, or "WIQL query"),
     generated-at, totals by status.
   - Linked TOC grouped by suite path (a single group for WIQL or ID input).
   - Each case with its own header; anchor `#tc-<id>`, or `#tc-<id>-<k>` for the k-th occurrence.
   - Step numbering restarts per case.
   - Markdown: equivalent headings and a TOC. JSON: the existing `cases` array with suite and
     source information; schema updated without breaking v1.
   - Rendering streams: TOC data comes from the collected cases, while case bodies are built and
     written one at a time.
7. **Export changes.** Remove the single-case limitation. File name: `TestSuite-<suiteId>-Steps.<ext>`
   when every case shares one suite ID, otherwise `TestCases-<yyyyMMdd-HHmmss>.<ext>` (local time,
   invariant culture). `data-case-count` equals the number of case occurrences. Validation counts
   every case and step. `-Open` opens the one committed file.
8. **Golden files.** A small multi-case document (3 cases, 2 suites, one case in both suites) in
   `en-US` and `fr-CA` for HTML, Markdown, and JSON. The 300-case document gets structural
   assertions, not a golden file.
9. **Tests.** S3-2, S3-4, S3-5, and Pester `BulkTestCase.Pester.ps1` (binding per input type,
   emission twice with `Suite`, one `FileInfo` for many piped cases, progress records present).
10. Run the offline done check (section 7).

## 10. Risks

| Risk | Mitigation |
| --- | --- |
| Testplan preview versions or routes differ on the server (V-04) | Registry-only change; fixtures marked [V-04]; the GA `test` area is the documented alternative |
| Suite child order is provisional | Take order from the server response; fixture marked; confirm in the live run |
| `AdoTestSuite.Id` binds to ById by property name and is used as a test case ID | Explicit parameter-set design plus Pester tests per input type |
| WIQL cap semantics (V-06): exactly 20,000 treated as possibly incomplete | Documented toolkit policy; `-Top` for intentional limits |
| Memory for very large exports (collected `AdoTestCase` objects) | Case bodies are rendered one at a time; objects share expanded step lists across memberships |
| Test time from generated 300-case fixtures pushes `project-check` toward 300 s | Generate once per test class; structural assertions only; track duration |
| Duplicate HTML ids for repeated cases | `#tc-<id>-<k>` rule (§12.5) with a test |
| Progress flooding slows the pipeline | Throttle progress events in the pump |
