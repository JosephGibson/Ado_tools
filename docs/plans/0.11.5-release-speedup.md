# 0.11.5 plan: faster releases

README version only, release automation, and a faster CI lint.

## Context

0.11.5 is a tooling-only version: the module is unchanged apart from its version number, as in
0.9.0 and 0.9.10. It starts after the pull request of 0.11.0 has been squash-merged and v0.11.0
published, on a branch `0.11.5` created from `origin/main` with the next-branch command of the
`release` skill. `VersionPrefix` stays at 0.11.0 while this plan is carried out; the 0.11.5
release session bumps it, through the new flow this plan builds.

Researched on 2026-10-05 from:
- the five most recent release sessions: 0.9.5, 0.9.10, 0.9.15, 0.10.0 and 0.10.5;
- the GitHub Actions runs of every release since 0.6.5;
- the code: `.agents/skills/release/SKILL.md`, the workflows, `tools/lib/validation.ps1`
  and `tools/package/`;
- current CI and release practice.

Nothing was changed during the research.
- **Line numbers** cited here are those of 2026-10-05, on the branch `0.11.0` before it merged.
  Find each place by its content before editing.
- **Phase 0** saves this plan as `0.11.5-release-speedup.md` under `docs/plans/`.

Files this plan creates are named without their full path in code spans, so the
`documentation` stage passes before they exist:
- `Release.Common.ps1`, `Start-AdoToolkitRelease.ps1`, `Test-AdoToolkitRelease.ps1` and
  `Complete-AdoToolkitRelease.ps1` in `tools/package/`;
- `Release.Tests.ps1` and `Lint.Tests.ps1` in `tools/tests/`;
- a new folder `unreleased/` under `docs/`, holding a `README.md`.

### Where a release session spends its time

| Release | Wall time | Tool calls | Full `verify` runs | Pre-fix proofs |
| --- | --- | --- | --- | --- |
| 0.10.5 | 18.3 min | 108 | 4 | 3.8 min, 13 fixes |
| 0.10.0 | 19.5 min | 114 | 5 | none |
| 0.9.15 | 14.5 min | 71 | 5, plus 2 after the handoff | none |
| 0.9.10 | 17.8 min | 82 | 4, plus 1 after the handoff | none |
| 0.9.5 | 28.7 min | 107 | 7 | 6.8 min |

- **Time by phase (average):**
  - validation: 7.5 min;
  - notes and changelog: 3.9 min;
  - orientation: 2.5 min (re-reading about 30 KB of previous notes, `docs/tooling.md` and the
    full diff);
  - bump, README and archive: 1.4 min;
  - handoff: 1.1 min.
- **Model time is 60–73 % of the wall time:** reading, thinking and composing, not tools. The
  notes are 23–41 KB; the 0.10.5 notes have 330 lines.
- **Gate runs:** 25 full runs over 5 releases, about 21 min. The procedure needs about 2. A local
  full `verify` takes 46–61 s.
- **Why the gate runs again:**
  - the validation section records counts from the gate (links, path references, test counts,
    durations), so writing it changes the count;
  - so the procedure is: run, write, run again, correct the counts, run again.
- **Validation rewritten every release:** each session writes its own validation script again.
  Examples:
  - `validate.ps1` in 0.9.0 and `Test-ReleaseAssets.ps1` in 0.10.0;
  - three or four inline calls in each of the others.
- **Pre-fix proofs:** each release rebuilds a runner by hand that restores released source,
  touches timestamps and checks `diff --stat`. Known pitfalls: the MSBuild timestamp (0.9.5) and
  a failure that only shows under code page 850 (0.10.5).
  - `fix-bug` step 2 already records the failing output when the test is written.
  - The 0.10.5 notes say the quality pass had already recorded the same failures.
- **README:** every release made 4–5 README edits:
  - the version line;
  - a new feature paragraph of 600–900 characters;
  - two links to the notes.
  - At 0.10.5, `README.md` lines 14–63 held a version history that repeats `CHANGELOG.md`. The
    0.11.0 release adds one more paragraph.
- **Local hashes:** the SHA-256 values that the notes record for local assets never match the
  published ones. CI builds its own assets, and the notes already tell the developer to compare
  with CI's `.sha256` files.

### Where the CI time goes

Durations of the `verify` step, by stage, from the JSON in the run logs:

| Run | Job | `verify` step | `powershell-lint` | `powershell-test` | `project-check` |
| --- | --- | --- | --- | --- | --- |
| Release v0.10.5 | 303 s | 231 s | 132.7 s | 92.0 s | 129.7 s |
| Verify 0.10.5 PR | 181 s | 135 s | 76.1 s | 55.7 s | 102.5 s |
| Release v0.10.0 | 304 s | 240 s | 144.1 s | 89.4 s | 137.7 s |
| Verify 0.10.0 PR | 282 s | 236 s | 141.4 s | 88.5 s | 136.9 s |

Every other step takes at most 20 s: checkout 7–8 s, the setup action 12–15 s, restore 14–20 s,
the version check 5–6 s, packaging 11–12 s, the portable check 3 s and the publish 6–8 s.

- **Lint is the problem.** `project-check` runs beside the in-process stages, and those run one
  after another (`tools/lib/validation.ps1`, `Invoke-ProjectVerification`).
  - `powershell-lint` plus `powershell-test` take 132–233 s, longer than `project-check`
    (102–138 s). The in-process chain is the critical path of every run.
- **Lint is 7–12× slower on the runner than locally.**
  - Measured locally on 2026-10-05 (16 logical processors): `verify -Stage powershell-lint`
    took 11.6 s for 71 files; `verify -Stage powershell-test` took 20.1 s.
  - On the runner (4 vCPU) lint takes 76–144 s.
  - `Get-PowerShellLintOutcome` (`tools/lib/validation.ps1:1-45`) calls `Invoke-ScriptAnalyzer`
    once per file, in sequence, in the `verify` runspace.
- **Hypothesis, unconfirmed:** module discovery.
  - The windows-2025 runner image ships `Microsoft.Graph` 2.40, `AWSPowershell` 5.0, `SqlServer`,
    `Az` 15.6 and others.
  - pwsh puts the Windows PowerShell module paths on `PSModulePath`.
  - PSScriptAnalyzer resolves command names through `Get-Command`, which auto-loads modules.
    `tools/lib/validation.ps1:885` records it for Pester. Each name it cannot resolve, such as a
    script's own functions, can trigger module discovery over those trees.
  - CPU contention with `project-check` on 4 vCPU adds to this, but cannot explain 12× on its
    own.
- **Faster tests do not shorten the release.** The required check is `verify`
  (ruleset 24468922). The tag job and the PR check run the same full gate on the same tree at
  the same moment.

## Decisions (developer, 2026-10-05)

1. **README:**
   - keep the `**Version X**` line, and link to `CHANGELOG.md`, which links every version's notes;
   - no per-version paragraph;
   - no row that links the latest notes.
2. **Release notes:** slim and generated.
   - The agent writes only what users read: what changed, visible changes, bug fixes, known
     limitations and the work-PC live checks.
   - A script generates the validation section from JSON.
   - Drop the link and file counts, the durations, the per-file code tables and the local
     SHA-256 values.
3. **Pre-fix evidence is recorded when the fix is made:**
   - `fix-bug` writes it, together with the rest of the fix's release text, to a change fragment;
   - the release only checks that every Bug fixes row carries evidence or a stated reason;
   - no source is restored at release time.
4. **CI:** fix the slow lint only. Out of scope:
   - running only the product gate in the release job;
   - splitting the PR check into jobs;
   - auto-merge.
   The section [Considered and not taken](#considered-and-not-taken) lists these alternatives,
   so that no session researches them again.
5. **Version:** this ships as 0.11.5, a tooling-only version after 0.11.0. 0.11.0 is released
   with the current procedure.

## Design

### D-1 README carries the version only

- **`README.md`:**
  - delete the per-version paragraphs between the introduction and the `[!NOTE]`;
  - keep their lasting sentences: what the changelog is for, and the profiles sentence with its
    link to the configuration file;
  - keep the installation and update instructions that 0.11.0 adds, including the text that
    names 0.11.0 as the first version with `Update-AdoToolkit`;
  - the version line keeps `**Version <VersionPrefix>**` as the only version line in the README;
  - in the Documentation table, delete the row "Release notes | Version …";
  - the changelog row says that each entry links its version's release notes;
  - the `[!NOTE]` on live validation stays: it is status, not history.
- **`docs/AGENTS.md`:** the `README.md` row gains the rule "carries the current version and no
  per-version history; `CHANGELOG.md` says what changed".
- **Test, in a new `Release.Tests.ps1` in `tools/tests/`:**
  - the README holds exactly one `**Version X.Y.Z**` line;
  - `X.Y.Z` equals `VersionPrefix` in `Directory.Build.props`;
  - the README links no `docs/release-<version>.md` file.
  - A bump that misses the README then fails `verify`. Today nothing checks it.

### D-2 Change fragments: release text and pre-fix evidence written at fix time

**The format:**
- One JSON file per change in the new `unreleased/` folder under `docs/`.
- Name: `<yyyyMMdd-HHmmss>-<slug>.json`, so the time orders the IDs.
- One file per change avoids conflicts between parallel worktree sessions.
- The `configuration` stage already parses JSON strictly.
- This is the changelog-fragment pattern of towncrier, scriv and changie, done here with
  one PowerShell assembler.

```json
{
  "kind": "fixed",
  "changelog": "One line that says what a user sees.",
  "visible": "Optional: the observable change, for the Visible changes section.",
  "contract": "Optional: a public contract change, for the release notes.",
  "finding": "What was wrong, its cause and the fix.",
  "regressionTest": "RetryPolicyTests.BodyReadErrorsAreRetriedOnlyWhenTheConnectionWasLost",
  "files": ["src/AdoToolkit.Core/Http/RetryPolicy.cs"],
  "testsChanged": "Optional: an existing test edited, and why.",
  "preFix": {
    "failure": "Assert.Throws() Failure: No exception was thrown",
    "totals": "Failed 1, passed 2, total 3",
    "condition": "Optional: when it fails, such as a console code page"
  }
}
```

**The fields:**
- `kind` is one of `added`, `changed`, `deprecated`, `removed`, `fixed`, `security` and
  `internal`. The first six are the changelog groups; `internal` reaches the notes only.
- `preFix` can be `{ "none": "<reason>" }` instead, for example `documentation`.
- `preFix` can be `{ "notReproduced": "<reason>" }` for a fix whose failure was not observed.
  The notes then say so: the skill's rule against claiming evidence that was not observed still
  applies.

**Who writes fragments:**
- `fix-bug`, as part of its step 5.
- The fix mode of `.claude/workflows/repo-review.js`.
  - Today `regression` in `FIX_SCHEMA` is optional free text (`.claude/workflows/repo-review.js:178-180`).
  - Phase 3 replaces it with a required `fragment` object for each fixed item, in the fragment
    format above.
  - For a code fix, that object holds either `preFix` with the observed failure and totals, or
    an explicit `none` or `notReproduced` reason. The schema refuses an item that has neither.
  - The gate step writes each `fragment` unchanged, so no area fixer needs to own the folder.
- Feature work writes a fragment for each user-visible change. A plan's
  "For the release notes" section still serves when there is none.
- **The session that carries out this plan** writes fragments for its own changes once Phase 2
  exists, so that the 0.11.5 release exercises assembly:
  - one `changed` fragment whose changelog line says the module is unchanged apart from its
    version number, as the 0.9.10 entry does;
  - one `internal` fragment per phase.

**Documentation:**
- The `README.md` in the new folder documents the format.
- A row in `docs/AGENTS.md` names the folder's reader, the `release` skill, and its rule: the
  release consumes the fragments and deletes them.

### D-3 Three release scripts

Each script prints one compact JSON document and exits `0`, `1` or `2`. Together they replace
what each session writes by hand today.
- They use only the Git commands that `AGENTS.md` allows: `rev-parse`, `show`, `status` and
  `log`.
- They never commit, tag or push.
- Generated files are written to a temporary file beside the target, validated, then replaced.
- They reuse `tools/package/Package.Common.ps1`, the discovery exclusions of `tools/dev.ps1`,
  and the checks that `New-AdoToolkitRelease.ps1` and `Assert-AdoPackage` already make; they do
  not repeat a check those already make.
- Shared code lives in `Release.Common.ps1`.

#### `Start-AdoToolkitRelease.ps1 -Version <new> [-Date <yyyy-MM-dd>] [-WhatIf]`

1. **Preconditions.**
   - Refuses on a detached HEAD, on `main`, or when the local tag `v<new>` exists
     (`git rev-parse --verify --quiet refs/tags/v<new>`).
   - When `gh` is present, refuses when the remote release exists (`gh release view`).
   - **A fresh preparation** requires `<new>` to be higher than `VersionPrefix`. Its first act is
     to record `<new>`, `<old>`, `<older>` and the base commit in `release-prep.json` under
     `artifacts/release/`, which Git ignores.
   - **A resumed preparation** is accepted only when `VersionPrefix` already equals `<new>` and
     `release-prep.json` names the same `<new>`. The recorded `<old>`, `<older>` and base are
     reused, never derived again from the bumped tree. Each step then checks its own end state
     and skips when that state already holds.
   - The base commit is the first commit in `git log` of HEAD whose subject starts with
     `AdoToolkit <old>:`.
2. **Bump.**
   - A table in the script names each declared version field and the pattern that holds it:
     - `VersionPrefix` in `Directory.Build.props`;
     - `**Version <old>**` in `README.md`;
     - the `AdoToolkit-<old>` zip names in `docs/guides/getting-started.md` and
       `tools/package/Install-AdoToolkit.ps1`.
   - Only those patterns are replaced; a bare `<old>` never is. From 0.11.0 on, the README, the
     guides and the release text name 0.11.0 on purpose, as the first version with
     `Update-AdoToolkit`.
   - Each file must have at least one replacement, and none of its declared patterns may still
     hold `<old>` afterwards. Otherwise the step fails and names the file. No fixed count is kept,
     so a guide that gains an example needs no change to the table.
3. **Archive the older notes** (`docs/release-<older>.md`), by the Archiving procedure of
   `docs/AGENTS.md`.
   - Move the file with a filesystem move.
   - Add the index row to `docs/archive/README.md`. The row text comes from the archived notes'
     one-line summary (D-4). Notes written before the template, the 0.10.5 and 0.11.0 notes
     among them, have none and get a `<!-- release:todo -->` marker instead.
   - Re-point every Markdown link in live documents whose resolved target was the old path,
     including anchors. This covers:
     - `CHANGELOG.md`;
     - the `<old>` notes;
     - the `V-nn` rows of `docs/archive/README.md`.
4. **Assemble from the fragments.**
   - Write the `## <new> - <date>` section of `CHANGELOG.md`:
     - groups in Keep a Changelog order;
     - `Details: [release notes](docs/release-<new>.md)`;
     - a marker bullet when no fragment carries a changelog line.
   - Write `docs/release-<new>.md` from the template (D-4):
     - Bug fixes rows numbered `R-1`, `R-2`, … in file-name order;
     - the pre-fix evidence in each row;
     - visible and contract items in their sections;
     - the generated carry-over rows;
     - markers where prose is owed.
   - **Journal before writing.** Before it writes either document, the step records in
     `release-prep.json` the fragment set it assembles: each file name with its SHA-256. After
     both documents are written, it marks assembly complete.
   - **The prep script deletes no fragment.** The finalize script deletes the journaled fragments
     as its last step.
   - **On a resumed preparation:**
     - assembly marked complete is skipped;
     - a fragment set that differs from the journal, by a file added, changed or missing, is
       refused with the differences named.
   - A fragment that fails validation stops the step before anything is written. Examples:
     a `fixed` fragment that names code files with no `preFix`, or an unknown `kind`.
5. **Leftovers.**
   - **Fails** only when a declared version field of the bump table still holds `<old>`.
   - **Reports, without failing,** every other discovered text file that holds `<old>`, with path
     and line. History files (`CHANGELOG.md`, `docs/release-*.md`, `docs/archive/`) are listed
     apart from the rest, for the agent to review in context.
   - Some old versions are meant to stay. On 2026-10-05:
     - `tools/tests/LiveAudit.Tests.ps1:784` tests that a 0.10.5 installation gets
       `UPDATE_CMDLET_REQUIRED`;
     - a comment at `src/AdoToolkit.Core/Update/UpdateHttp.cs:57` sizes caps against the
       0.10.5 assets;
     - from 0.11.0 on, the update instructions name 0.11.0.
   - This replaces `find -Query '<old>'`, which reports one line per file.
6. **Output:** old, older and new versions, the base commit, the files changed, the fragment
   count and the markers left to fill.

#### `Test-AdoToolkitRelease.ps1`

Started in the background right after the prep script, while the agent writes the prose.

- **Release-build mode for every step.** The script sets `ADOTOOLKIT_RELEASE_BUILD=1` in its own
  process environment, so every child inherits it: `verify`, `Publish-AdoToolkitPackage.ps1`,
  `New-AdoToolkitRelease.ps1` and `Test-AdoToolkitPortable.ps1`.
  - `Get-BuildModule` (`tools/lib/dependencies.ps1:66`) selects the exact pins only under that
    variable.
  - `Publish-AdoToolkitPackage.ps1 -NoBuild` still compiles help with PlatyPS, so without the
    variable it would pick the highest installed PlatyPS 1.x instead of the pin.
  - The variable is never set in the agent's shell.
- **Content hash before and after.** Before the gate, the script hashes the content and the
  membership of every discovered file except `CHANGELOG.md`, `docs/release-<new>.md` and
  `docs/archive/README.md`. It hashes them again after packaging.
  - A difference fails the check: something changed while the gate ran.
  - The pre-gate hash is the one recorded for the finalize script.

1. **The gate.** Runs `verify`.
   - It runs every stage but `documentation`. With `-Stage` the exit code is always `2`, so the
     script reads each stage's status from the JSON.
   - The `documentation` stage runs in the finalize script, because the agent is still writing
     the notes.
   - The release-build run is the stricter of today's two runs, so the plain run goes.
   - The stage names are passed as an array, through `-Command` or a direct call. `pwsh -File`
     turns `a,b` into one string.
2. **Version.** `dotnet msbuild … -getProperty:Version` equals `<new>`.
3. **Packaging.** Packages the verified build with `Publish-AdoToolkitPackage.ps1 -NoBuild`, as
   the release workflow does, instead of rebuilding with `-NoRestore`.
4. **Release assets.**
   - `New-AdoToolkitRelease.ps1` writes them, with the runtime from
     `artifacts/runtime-download/` when it is there.
   - Without the runtime, the portable asset is reported as not built locally (status
     `incomplete`), as the skill allows today.
   - Then `Test-AdoToolkitPortable.ps1`.
5. **Remaining checks**, only those not already made by the scripts above:
   - the zip entries and `bundle.json` against the setup action's `POWERSHELL_SHA256`;
   - `Install-AdoToolkit.ps1 -Path <module zip> -WhatIf`;
   - `gh` presence from `diagnose`.
6. **Output.** Written to stdout and to `release-check.json` under `artifacts/release/`:
   - the stage statuses, the per-suite test counts and the module pins;
   - the asset names and sizes;
   - the portable status;
   - the pre-gate content hash, which the post-packaging hash matched.

#### `Complete-AdoToolkitRelease.ps1 -Summary '<summary>'`

1. **Refusals.** Refuses when any of the following holds:
   - a `release:todo` marker remains in `CHANGELOG.md`, the new notes or the archive index;
   - `release-check.json` is missing, or its status is not `pass` (or `incomplete` only for the
     portable asset);
   - the current content hash, of content and membership, differs from the pre-gate hash. The
     source changed after the gate started, so the check runs again.
2. **Validation section.** Writes it between `<!-- release-check:begin -->` and
   `<!-- release-check:end -->` in the notes, from the JSON:
   - it holds the gate result with the pins, the test counts and the assets with sizes;
   - it holds no link counts, durations or local hashes;
   - it adds no link, so it cannot change what the documentation stage counts.
3. **The rest of the gate.**
   - Runs `verify -Stage documentation`, reading the stage status from the JSON.
   - Runs the `CHANGELOG.md` and README tests: `Release.Tests.ps1`, and the CHANGELOG `It` of
     `tools/tests/ReleaseWorkflow.Tests.ps1`, with Pester 5.9.1 imported first.
4. **Fragments.** Deletes the fragments that `release-prep.json` journaled.
   - The deletion is idempotent: a file already gone counts as deleted, so a rerun after an
     interruption between deletions completes it.
   - It comes after the hash comparison and the checks above, so the release commit holds no
     fragment.
5. **Handoff.** Prints the filled handoff:
   - branch and remote, from `git status --short --branch`;
   - a confirmation that the tag `v<new>` does not exist;
   - the title `AdoToolkit <new>: <summary>`. The summary may hold no quote.
   - the three command lines that SKILL.md writes by hand today: commit, tag, push and PR;
     `gh pr checks --watch` then `--web`; and the next branch.

   The command templates move from SKILL.md into this script, so they live in one place and a
   test checks them.

**Rationale for splitting the gate:** the check script runs every stage but `documentation`,
and the finalize script runs `documentation` and the two document tests.
- Only the three allowed documents change between the two runs, and the content hash proves it.
- Together the two runs cover the full gate on the final tree.
- The skill's write, run, correct and run-again loop goes away.
- The tag job and the PR check still run the full `verify`.

**Fallback,** if the developer wants one uninterrupted full run before the handoff: the finalize
script runs the full `verify` again, for about 1 more minute.

### D-4 Slim notes template

The template lives inside `Release.Common.ps1` as a here-string. A Markdown file holding
`release-<new>.md` links would fail the `documentation` stage.

| Section | Source |
| --- | --- |
| Title, then a one-line summary | The agent. The archive row reuses the summary later |
| Opening: date, branch, base commit, live-validation status | The prep script writes date, branch and base; the agent writes one or two sentences |
| What changed | The agent: final behavior by area. One table per area at most, no per-file code tables |
| Visible changes for `<old>` users, and Public contract changes | Fragments, then the agent |
| Bug fixes: ID, finding with cause and fix, regression test, files, pre-fix failure | Fragments only |
| Existing tests changed | Fragments; the section is left out when empty |
| Findings not fixed | The agent writes the new rows. The prep script generates the carry-over row (below) |
| Known limitations | The agent writes the new rows. The prep script generates the carry-over row |
| Work-PC live checks | The agent |
| Validation | Generated by the finalize script |

**Carry-over rows.** These keep the form they have today: one link per earlier version, to its
"Findings not fixed" or "Known limitations" section.
- **Why not a single link to the previous notes:** archived notes are frozen and their relative
  links stop resolving (`docs/archive/README.md:3`). A chain of single links therefore breaks
  after one archive.
- **How the prep script builds them:**
  - it takes the list from the previous notes' carry-over row;
  - it adds the previous notes themselves;
  - it points each link at where that file is now, in `docs/` or in `docs/archive/`.
- The agent writes none of these links, and the `documentation` stage checks every one, anchors
  included, as it checks release-notes links today.
- A test archives through two successive cycles and checks that every carry-over link still
  resolves.

**Dropped:**
- the Code, Tests and Documentation tables;
- the separate Pre-fix failures table, now merged into Bug fixes;
- the developer handoff steps, which stay in the skill's reply;
- the local SHA-256 table.

### D-5 The release skill, rewritten

`.agents/skills/release/SKILL.md` shrinks from 199 lines to about 60. The steps:

1. Run `Start-AdoToolkitRelease.ps1 -Version <new>`, and stop on failure.
2. Start `Test-AdoToolkitRelease.ps1` in the background.
3. **Orientation.** Read:
   - the prep JSON;
   - `git diff --stat` against the base, then the diff of the changed product files;
   - the "For the release notes" section of any plan for the version.

   Do not read earlier notes for their structure: the template sets it.
4. **Prose.** Replace each marker:
   - the changelog bullets that no fragment supplied;
   - the opening, What changed, Findings not fixed, Known limitations and Work-PC live checks;
   - the summary line;
   - the archive row of notes written before the template.
5. Wait for the check to finish. If it fails, report the command, the code and the failures,
   then stop.
   - A failure that passes on a repeat of the same command, and that nothing in the release
     touches, is a flake. Record it, as the skill says today.
6. Run `Complete-AdoToolkitRelease.ps1 -Summary '<summary>'`. Relay its handoff commands, the
   gate result, the assets, the contract changes and the unfixed findings.
   - Keep the warning that command 1 publishes the moment it pushes the tag. From 0.11.0 on,
     users who run `Update-AdoToolkit` receive it at once.

**Kept from today:**
- the developer is the author, with no attribution;
- no Git writes;
- the version rules and the archiving rule;
- the flake rule;
- the `gh` and token notes, shortened.

### D-6 A faster CI lint

1. **Reproduce locally**, without installing anything.
   - Measure `verify -Stage powershell-lint` as it is.
   - Then measure it with a synthetic module tree on `PSModulePath`, generated under the session
     scratchpad: about 50 module folders whose manifests export a few hundred functions each.
   - If lint slows by several times, the discovery hypothesis holds.
   - Also measure `powershell-test` under the same tree.
2. **Isolate lint.**
   - `Get-PowerShellLintOutcome` runs `Invoke-ScriptAnalyzer` in a child `pwsh` process.
   - **The child's `PSModulePath`** holds only:
     - `$PSHOME\Modules`;
     - the folders of the three build modules that `Get-BuildModule` selects: PSScriptAnalyzer,
       Pester 5 and PlatyPS 1, exact pins under `ADOTOOLKIT_RELEASE_BUILD`.
   - **Why the build modules stay visible:** the scripts call Pester and PlatyPS commands, and
     PSScriptAnalyzer validates a call only when it resolves the command.
     `tools/lib/validation.ps1:885` records that resolving `Describe`, `It` and `Should`
     auto-loads Pester.
   - **The child imports the selected Pester first,** as `Invoke-ProjectVerification` does
     today, so the highest installed Pester, possibly 6.x, never auto-loads.
   - **Lossless results.** The child writes its findings as JSON to a result file in the system
     temporary folder, outside the repository. The caller reads the file after the process exits
     and deletes it in a `finally` block.
     - Stdout is not used: `Invoke-BoundedProcess` keeps only 120 lines of at most 2,000
       characters each (`tools/lib/validation.ps1:786-787`), which would truncate a large
       result.
     - The process still runs with its timeout and its process-tree stop, as
       `Invoke-BoundedProcess` gives today.
     - An in-process stage writes nothing to `bin/`, `obj/` or `artifacts/`, so the result file
       goes nowhere in the repository.
   - The file list is still the one discovery enumerated: the analyzer never recurses.
   - **Effect:** lint no longer scans the runner's other module trees (Microsoft.Graph,
     AWSPowershell, Az), and it gives the same result locally and in CI.
3. **Overlap lint with the tooling tests.**
   - Conditional: only if step 1 shows contention matters, or the 0.11.5 PR run after step 2
     still shows lint above 30 s.
   - Start the lint child process when `verify` starts, and collect it in the `powershell-lint`
     stage's turn.
   - Stage names, their order, the outcome fields and `DurationMs` stay as the stage contracts
     define them.
4. **Optional:** analyze files in parallel inside the child process, a few runspaces at a time.
   Only if measured to help and if PSScriptAnalyzer gives identical findings.

**Tests,** in a new `Lint.Tests.ps1` or the existing stage tests:
- a seeded violation is still reported with path, line and rule;
- a seeded invalid call to a build-module command is still reported. An example is a Pester or
  PlatyPS command missing a mandatory parameter, which PSUseCmdletCorrectly flags. This proves
  command validation survives the isolation;
- a parse error is still reported;
- every finding arrives when the result is large: more than 120 findings, and serialized
  output longer than 2,000 characters on one line;
- a missing analyzer still makes the stage `unavailable`;
- the findings do not change when the caller's `PSModulePath` holds an extra synthetic module.

Timing is evidence in the handoff, not an assertion, so no test is flaky.

### Deviations from the design

- **D-6 step 2.** The analyzer cannot be held to the pinned build modules. PSScriptAnalyzer
  resolves commands in runspaces of its own, and PowerShell puts the user's and the shared
  PowerShell 7 module folders first in every runspace it opens, ahead of any folder on the path
  (tested 2026-10-05). The child therefore sets its module path to `$PSHOME\Modules`, imports only
  the selected PSScriptAnalyzer by path, and lets a call to a build module resolve from those
  three folders, the highest version first, as the runspace of `verify` did before. The Windows
  PowerShell folders and every other folder on the path of `verify` are left out.
  `tools/tests/Lint.Tests.ps1` shows that a module that shadows a PlatyPS cmdlet on the caller's
  path no longer changes the findings; in the runspace of `verify` it hid a finding.
- **D-4 carry-over rows.** The list comes from the previous notes' rows; a row that links a single
  version hands over to that version's list, as the 0.11.0 notes hand over to the 0.10.5 notes. A
  full closure over every archived note would bring back the 0.6.x limitations, which later
  notes dropped on purpose.
- **D-3.** The function behind the prep script takes `-DryRun`: PSScriptAnalyzer refuses a
  `-WhatIf` switch on a function without ShouldProcess, and ShouldProcess would print lines beside
  the JSON. The script keeps a plain `-WhatIf` switch. The handoff goes to
  `artifacts/release/handoff.md` as well, so its commands are relayed byte for byte instead of
  being decoded from JSON. The fragments are left out of the content hash; the journal covers them.
- **D-5.** The skill starts with a `-WhatIf` run that compares the fragments with the diff, and
  writes a missing fragment before the preparation, which journals them; 82 lines instead of
  about 60.
- **D-2.** `docs/unreleased/` belongs to the README, guides and release notes area of
  `repo-review`, in `AREAS` and in `.claude/agents/area-reviewer.md`. A deferred edit may carry the
  fragment of a fix made entirely through it, and the workflow keeps one fragment per finding.
