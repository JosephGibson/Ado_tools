# 0.12.0 plan: an error classifier for the failed-test report

Every failed attempt classified, generic errors set apart, and English and French forms of one
error merged.

## Context

At work, By error does not sort failures usefully, for three reasons:
- **One error per test.** `ErrorClusters.Of` (`src/AdoToolkit.Core/Reporting/TestFailures/ErrorClusters.cs:55-92`)
  keys each test by the attempt that `HtmlTestFailureRenderer.LatestErrorAttempt` picks
  (`src/AdoToolkit.Core/Reporting/TestFailures/HtmlTestFailureRenderer.cs:55-57`). The errors of
  the other attempts reach neither By error, Most common errors nor "Same error, not linked".
- **Generic failures** (home page down, WebDriver session lost, HTTP 503) form the largest
  clusters, and they hide the specific errors of the same test's earlier attempts.
- **Two languages.** The English and French stages run the same tests, and the key is the literal
  text. The 0.8.5 notes already list this as a known limitation: "text in another language, or a
  different wording of the same failure, stays apart" (`docs/archive/release-0.8.5.md:172`).

**Research, 2026-10-06, on branch `0.12.0` at f494b12.** Nothing was changed.
- **Code read:** the clustering, the renderer, the CSV renderer, the attempt mapper, the history
  read, the configuration store, the validator, the script and its tests.
- **Text sources:** the NuGet cache and local runtime resources, and the REST 6.0 reference for
  result listings.
- **Line numbers** are those of that commit. Find each place by its content before editing.
- **New files** are named without a full path in code spans, so that the `documentation` stage
  passes before they exist.
- **Phase 0** saves this plan as `0.12.0-error-classifier.md` under `docs/plans/`.

## Decisions (developer, 2026-10-06)

1. **Rules:** one global list, `reporting.errorRules`, of named rules. Each rule has wildcard
   patterns in any language and `generic`, which defaults to true. With `false`, the rule only
   merges its matches and names them.
2. **Spread:** shown, never used to demote an error.
3. **CSV:** four columns at the end: `Primary error`, `Error kind`, `Error rule`, `Distinct errors`.
4. **Across builds:** in 0.12.0, as the last phase, with the V-39 probe.
5. **Merging forms:** two forms are paired across pipeline groups by tests that fail at the same
   place. Quoted text is not turned into slots: the direction proposed slots, which this replaces.
6. **Packages:** the framework packages are downloaded into the session scratchpad and read there
   during implementation. Nothing is installed and the project does not change.
7. **MSTest versions:** unknown, so the catalog holds the latest 2.x, 3.x and 4.x forms.

## Findings that shape the design

- **F-1 Slots for every quoted value would merge the near misses.**
  - Today a key keeps quoted and `<…>` text literal (`ErrorClusters.cs:215`).
  - As slots, `Expected:<Welcome>` and `Expected:<Cart>` would get one key. So would every
    selector of `Unable to locate element`, which the stay-apart cases forbid.
  - xUnit's key line, `Assert.Equal() Failure: Values differ`, carries no value at all: the
    expected value is on the next line.
  - So each template hole gets a role, and the two languages merge on evidence, not on shape.
- **F-2 What could be confirmed locally:**

  | Source | Evidence | Result |
  | --- | --- | --- |
  | xUnit v3 | `xunit.v3.assert` 4.0.1 in the NuGet cache: strings read from the assembly; no satellite assembly | English confirmed; there is no French form |
  | .NET 10 | Shared runtime resources (CoreLib, System.Net.Http, System.Linq); `Microsoft.NETCore.App` 10.0.11 has no `fr` folder | English confirmed; on .NET the runtime text is English whatever the culture |
  | .NET Framework 4.8 | mscorlib, System and System.Net.Http resources through Windows PowerShell 5.1; no French language pack | English confirmed; French → V-41 |
  | Windows socket messages | `Win32Exception` 10060, 10061, 11001 in English; `System32\fr-FR` holds no system message file | English confirmed; French → V-41 |
  | MSTest, NUnit, xUnit v2, Selenium | Not in the cache | Read from the downloaded packages in phase 2 |
  | Browser drivers (chromedriver) | In no package | V-42 |
  | Test platform `fr` resources | `microsoft.testplatform.*` 18.10.1 and `microsoft.testing.platform` 2.4.0 | No per-test text |

  The trace lexer already reads French .NET Framework frames: `at`/`à`, `in`/`dans` and
  `line`/`ligne` (`src/AdoToolkit.Core/Reporting/Highlighting/StackTraceLexer.cs:7-12`).
  V-29 records that the agents' runtime language is unconfirmed.
- **F-3 The result listing carries the error message, by the documentation.**
  - The REST 6.0 reference for Results - List defines `ResultDetails.none` as "Core fields of
    test result. Core fields includes State, Outcome, Priority, AutomatedTestName,
    AutomatedTestStorage, Comments, ErrorMessage etc.".
  - Its sample listing, which has no `detailsToInclude`, returns `errorMessage` and `stackTrace`
    on the failed result.
  - V-34 records that lists on Azure DevOps Services cut messages at 4,000 characters
    (`docs/archive/release-0.8.0.md:203`).
  - Server 2020 is unconfirmed → V-39.
  - `TestResultListingDto` reads eight fields under §15.9 step 3
    (`src/AdoToolkit.Core/TestRuns/TestRunDtos.cs:59-71`), a decision that stands
    (`docs/archive/release-0.8.0.md:209`). Phase 4a revisits it.
- **F-4 Limits the change must respect:**
  - The script must stay under 16 KiB, and about 3 KB are left (`ScriptAssetTokenScanTests`).
  - The script hides any `.error-cluster` with no `tr[data-index-for]` row
    (`src/AdoToolkit.Core/Reporting/Assets/test-failures.js:109`).
  - The 200 × 14 report must stay under 54,100,000 bytes; it measured 52,911,987
    (`tests/AdoToolkit.Core.Tests/Reporting/TestFailures/ErrorTextTests.cs:58-106`).
  - Any CSS edit rewrites all 12 failed-test goldens.
  - The validator checks no structure of By error, the Overview cards or Open bugs; tests pin
    those views.
- **F-5 Fixtures.**
  - No report fixture has a translated pair.
  - Only `grouped`'s SubmitOrder fails differently in two attempts.
  - `large`'s two NullReferenceException tests fail in the same frame,
    `PaymentsClient.Refund`, so keying them by frame keeps their cluster.
- **F-6 Two reading rules.**
  - The latest attempt is the one with the highest number. Retrieval numbers attempts in run
    order across groups (`TestFailureRetrievalService.cs:263-269`).
  - A data-driven parent keeps its own message, as today; the messages of its sub-results stay
    in the card.

## Design

### D-1 Attempts and error text

- **Occurrences.**
  - Every attempt whose `OutcomeClass` is `Failure` and that has a key line is one occurrence.
  - When a test has none, the attempt that `LatestErrorAttempt` picks today is used once, and
    its placement says it did not fail.
  - A test with no key line at all goes to the tests without an error message.
  - Classes are built from every failure of the set, flaky tests included, so `-IncludeFlaky`
    changes which rows show, never which classes exist.
  - Occurrences are keyed by the test and the attempt number, never by object: an export copies
    failures and attempts after its downloads (`AttachmentDownloader.cs:81`).
- **Folding, used only to match.**
  - Decompose (NFD), drop nonspacing marks, then lower-case with the invariant culture.
  - Map `’ ‘ ʼ` to `'`, and U+00A0, U+202F and U+2009 to a space.
  - Collapse runs of white space to one space, and trim.
  - An offset map points back into the text as sent, so every displayed part and value is the
    server's text. A cut never splits a surrogate pair (`HtmlTestFailureRenderer.cs:40-43`).
- **Lines read.**
  - The key line (`ErrorClusters.KeyLine`, moved to `ErrorText.cs`) and the first line.
    `KeyLine` keeps returning what it returns today: every attempt summary shows it
    (`ByErrorViewTests.cs:118-132`). The catalog's wrappers apply to signatures only.
  - A multi-line template also reads the lines it names, up to four.
  - Lines are read whole, as 0.8.5 keys on the whole first line, so two messages that differ
    late in a long line stay apart. Only a listing's text is cut, by the server (D-8).
- **Memoized.** Each distinct input (lines, exception type, own frame) is classified once, so a
  test's 14 identical attempts cost one classification.

### D-2 Catalog of templates

- **Families:**
  - MSTest assertions (`FrameworkMessages`);
  - MSTest adapter texts: the "threw exception" wrapper, initialization, cleanup and timeout;
  - NUnit 3 and 4;
  - xUnit v2 and v3;
  - Selenium WebDriver and Support.
- **A template** has:
  - an ID of letters only, such as `MsTestAreEqual`;
  - its English and French forms, one per package version that differs;
  - holes, each with a role.
- **Hole roles:**
  - **identity** is part of the key: an expected value, a selector, a method, or the user message
    after the template, tokenized as in D-1;
  - **value** varies and shows in Values: an actual value, a test name, a duration.
- **Located templates** add the test's own first frame (`RootFrame`, `ErrorClusters.cs:149-155`)
  to the key when they have no identity text. Examples:
  - IsTrue, IsFalse, Fail, IsNull and IsNotNull without a message;
  - xUnit True, False, Null, NotNull and Fail;
  - NUnit `Expected: True`;
  - the WebDriverWait timeout without a message;
  - stale and non-interactable elements.
- **Default messages** are ignored for `NullReferenceException`, `IndexOutOfRangeException`,
  `DivideByZeroException`, `OperationCanceledException` and `TaskCanceledException`.
  - A message that is the type's default text, as confirmed from the local runtime resources,
    is ignored, and the key is the type and the own frame.
  - A custom message stays identity, such as `OperationCanceledException("Simulated stop")`
    (`tests/AdoToolkit.Core.Tests/IO/GenerationFolderCommitTests.cs:78`).
  - The French default texts are unconfirmed (V-41). Until then, pairing merges them.
- **Without an own frame** (no trace, or a test without a name), a located template or a default
  message keys on its text, as today.
- **Wrappers.** MSTest's wrapper, in both languages, is a catalog wrapper. The key line is then
  the exception below it, as today, in French too.
- **Sources.**
  - Each form cites its package and version, or the local runtime, in a code comment.
  - A form that cannot be confirmed stays out of the catalog, and its V-nn item says so. No form
    is written from memory.
- **Matching:** templates are `RegexOptions.NonBacktracking | CultureInvariant` patterns run on
  folded text, as `ErrorMessageLexer` does (`src/AdoToolkit.Core/Reporting/Highlighting/ErrorMessageLexer.cs:7-9`).

### D-3 Pairing across groups

- **Fingerprint.**
  - The frames of the test's own root namespace, method and line number, at most 8 from the
    first 64 lines of the trace.
  - They are read by a new `StackTraceLexer` member that returns method and line; `FirstFrame`
    returns the method only.
  - A frame without a line number compares by its method alone.
  - There is no fingerprint without such a frame.
  - A missing exception type pairs only with a missing one.
- **Language evidence.** A group's language comes from the catalog forms recognized in it that
  exist in both languages, such as MSTest's wrapper and assertions. It is English, French, or
  unknown when the group has none or both.
- **Pairing.**
  - Only an English group and a French group pair. Two English jobs never do, whatever their
    names, because pipeline groups are also jobs and runs
    (`src/AdoToolkit.Core/TestRuns/PipelineGrouping.cs:83`).
  - Two recognized forms of one template in the same language never pair: their identity
    values differ in that language.
  - Tests are visited in ordinal order.
  - Each test's occurrences are bucketed by exception type and fingerprint.
  - A bucket with no fingerprint is skipped, and so is one that holds two forms in one group.
  - Otherwise, the forms of each English and French group in the bucket are united.
- **Invariant.** A class holds at most one form per pipeline group. A union that would break it
  is refused. A build without groups never pairs.
- **Evidence.** Each union records the test and its two groups. The facts show, for example,
  "Forms: 2 · Paired by SubmitOrder (Tests_EN, Tests_FR)".
- **Determinism.** The order matters only through refused unions, and the visit order is fixed.

### D-4 Rules

**Built-in rules.** All are generic. Their names are in both catalogs, and the CSV shows their
IDs.

| ID | Matches | Source |
| --- | --- | --- |
| `ConnectionRefused` | "No connection could be made because the target machine actively refused it", `net::ERR_CONNECTION_REFUSED` | Winsock 10061 (en), Chrome |
| `NameResolution` | "No such host is known", "The remote name could not be resolved", `net::ERR_NAME_NOT_RESOLVED` | Winsock 11001, .NET Framework |
| `ServerUnavailable` | `: 502 (`, `: 503 (`, `: 504 (` or `(502)`, `(503)`, `(504)` on a line that also names `HttpRequestException` or `WebException`, or holds "Response status code does not indicate success" or "The remote server returned an error". Selenium often wraps these mid-line | .NET 10, .NET Framework; the status shapes do not depend on the language |
| `WebDriverSession` | "session not created", "invalid session id", "no such window", "chrome not reachable", "disconnected: not connected to DevTools", "The HTTP request to the remote WebDriver server for URL * timed out after * seconds" | Selenium (phase 2); driver texts V-42 |
| `PageLoadTimeout` | "timeout: Timed out receiving message from renderer" | Driver text, V-42 |

**Matching.**
- Configured rules are tried first, in file order, then the built-in ones. The first match wins.
- A rule merges its matches into one class, under its name.
- A pattern uses `*` and `?` and must match a whole line, after folding. It is tried on the key
  line and on the first line, each with and without a leading `Type: `.
- The matcher runs in linear time: segments between stars are found left to right, and `?` is
  matched by a shift-and search. It uses no regular expression and needs no timeout.
- A pattern runs only on a line that contains its longest literal segment, found by a
  vectorized search. Even 2,000 patterns on a 1 MiB line stay a fraction of a second.
- Patterns are compiled for each report, never kept in a static, which would be session state
  (`src/AGENTS.md`).

### D-5 Error profile and primary error

- **Profile.** For each class of a test: its attempts, its groups, the number of its latest
  attempt, and the occurrence that is shown.
- **Primary error.**
  - The most frequent class that is not generic. On a tie, the class of the latest attempt.
  - A test with only generic classes takes the most frequent of them, with the same tie rule.
- **Placement text:**
  - "{n} of {m} failed attempts", where m counts failed attempts with or without a message;
  - "…, the latest" when a tie decided;
  - "From an attempt that did not fail".
- **Other errors.**
  - The test's other classes, the most frequent first, as "label ×count".
  - The label links to the class's cluster: every class has one (D-6).
  - The label is the rule name, else the short exception type, else the line cut at 60
    characters. Its title is the line.

### D-6 Report

**By error.**
- **Clusters.** Every class that a test hit in a failed attempt is a cluster, so an error that
  is no test's primary error still shows.
- **Rows.**
  - A test's row sits in the cluster of its primary error.
  - Under each of its other errors the test appears again, muted (`related`, as Open bugs shows
    a test of the same Test Case). The muted row has that error's own placement text and a link
    to the primary cluster.
- **Counts.** A heading's count is the tests whose primary error it is, then "+k" for its other
  tests. Its title says both in words.
- **Summary line:** "Distinct errors: n · Generic: g · Tests: m".
- **Order:**
  1. specific clusters, by the tests whose primary error they are, then by all their tests, ties
     by first ordinal;
  2. a section row group (`cluster-section`, id `generic-errors`): the heading "Generic errors"
     and one sentence that says what made them generic.
     - It is a row of the same table, so 0.8.5's single table and its rule of no nested
       `<section>` hold (`docs/archive/plans/0.8.5-report-styling.md:36`, `:225`).
     - Its row is the Runs table's `group-heading` row (`th scope="rowgroup"`).
     - The section deliberately changes 0.8.5's order of largest first and no message last
       (`:235-236`);
  3. the generic clusters;
  4. the tests without an error message.
- **Cluster heading:** count, exception type, the rule name (`cluster-rule`) when a rule placed
  the cluster, then the line.
- **Facts row:** today's facts plus:
  - spread: "In n tests of k classes", counting every test with the class in any failed attempt;
  - the number of forms, and the tests that paired them.
- **Values column:**
  - members whose shown occurrences share one layout (one template or one tokenized skeleton)
    show their varying values, as today;
  - in a cluster of several forms, each member shows its own key line.
- **Sample:** the latest attempt that carries the cluster's error, not the test's latest error
  (`HtmlTestFailureRenderer.cs:518-519`). A cluster of several forms shows its first member's
  line, without marks.
- **Rows:** a new last column, **Errors**, with the placement text and the other errors.
- **Validator:** it also checks that every in-page link has a target, which catches a dangling
  `#e-N`.
- **Script:** the section row hides when every generic cluster is hidden. It stays clear of
  `.error-cluster`, and the generic clusters carry `data-generic`. About 150 bytes.

**Overview.**
- Most common errors lists the specific errors that the most tests hit in any failed attempt:
  still at least two tests, the three largest, each opening its cluster.
- A new card, **Generic errors**, comes after it: "With a generic error: n" and "Only generic
  errors: m". It is left out when n is 0. It links to `#generic-errors`, which exists whenever
  n > 0, because every error a test hit has a cluster.
- The table keeps **Latest error**, as the console does (0.8.5 decision).

**Open bugs.** `SameError` (`HtmlTestFailureRenderer.cs:637-649`) starts from the primary error
of each linked test, as the direction asks.
- It counts the tests that hit that error in any failed attempt and are neither linked nor of
  the same Test Case.
- Each test counts once, across all the linked tests' errors: a union of tests, not the sum per
  cluster of `HtmlTestFailureRenderer.cs:644-645`, because clusters now overlap.
- It opens that error's cluster, which always exists.
- `ClusterOf` becomes a test's primary cluster, and a membership lookup is added beside it.

**Details.** Unchanged. Cards keep `data-latest-error`, so reaching a test opens its latest
error, as the guide says (`docs/guides/build-report.md:183-184`).

**CSS.** New rules for `.cluster-section`, `.cluster-rule`, `.col-errors` and `.other-errors`.
This regenerates all 12 goldens, through `update-goldens`.

**CSV.**
- `Primary error`: the whole message of the primary class's latest occurrence.
- `Error kind`: `Specific`, `Generic`, or empty.
- `Error rule`: a configured name as written, or a built-in ID.
- `Distinct errors`: the number of classes among failed attempts.
- `Validate` checks the new width.

### D-7 Configuration

- **`reporting.errorRules`:** an array, empty by default, of at most 100 rules.
  - `name`: 1–100 characters after trimming, unique ignoring case.
  - `patterns`: 1–20 strings, each 1–500 characters and not blank.
  - `generic`: a Boolean, true by default.
- **Errors.** An invalid value is an `AdoConfiguration` error, as for the other keys. An unknown
  key inside a rule warns with its path, such as `reporting.errorRules[0].x`.
  - The message names the rule and the property, through a new `InvalidErrorRule` message.
    `InvalidConfiguration` shows only the exception type (`ConfigurationStore.cs:119`).
  - As for every key, a bad rule fails every cmdlet that reads the file. The guide says so.
- **Writing.** `Serialize` writes the typed rules, as it writes `culture` from its typed
  property (`src/AdoToolkit.Core/Configuration/ConfigurationStore.cs:207-209`). A rule set only
  in `ReportingOptions` is then never lost on save.
  - Each rule starts from the node of the same name as read, so its unknown keys survive. This
    is how profiles are written (`ConfigurationStore.cs:173`).
  - `generic` is written when it is false, or when the node had it.
  - The key is left out when there is no rule and the file had none.
  - **Tests:** a typed configuration through `Serialize` and `Parse`, and a file with rules
    through `SetProfile`, keep every rule and every unknown key.
- **Flow:** `ReportingOptions.ErrorRules` (new `ErrorRuleOptions`) → `ExportAdoBuildTestFailureCommand`
  → `TestFailureExportOptions` → `TestFailureExporter.Prepare` → `TestFailureReportOptions` →
  `TestFailureReportModelBuilder.Build`.
  - `Build` classifies every failure of the set once, because the model holds only the failures
    it shows (D-1).
  - The model carries the result internally, for both renderers.
  - `WithAttachments` copies it (`TestFailureReportModelBuilder.cs:87-97`).
- **Where it applies.** `Get-AdoBuildTestFailure` reads no rule, and `AdoTestFailure` and its
  console table do not change. The classifier stays in a new folder `Errors/` under
  `src/AdoToolkit.Core/Reporting/`, because no output type needs it.

### D-8 Across builds

- **Listing.** `TestResultListingDto.ErrorMessage` is the ninth field. `ToRecord` keeps the start
  of a failed record's message: its first lines, as many as the longest template reads (D-2),
  never the rest.
  - It is read leniently: a value that is not a string reads as no message. A strict field
    would fail the whole listing (`AdoHttpPipeline.cs:92-94`), and so pass 1 or a history build
    (§15.12).
  - The DTO's comment records the deviation from §15.9 step 3, as
    `TestFailureRetrievalService.cs:10-12` records its own.
- **History data.**
  - `HistoryBuildData.Errors`: for each identity, the distinct message starts of its failed
    records, at most five, and whether more were dropped. `TestFailureInvocationCache` keeps
    them with the build.
  - `AdoTestHistoryEntry.ErrorMessages` (public): those starts, as the listing sent them.
    - It is empty for the current build, for a build without failures, and when the listing
      carried no message.
    - It is not `required`, so hand-made entries still pass the input check
      (`InputGuard.cs:31`).
  - `CurrentBuildData` copies the new data (`TestFailureRetrievalService.cs:425-433`), and the
    cache's comment names it.
- **Report.**
  - The previous failed build of a test is the latest earlier entry that is `Failed` or `Flaky`
    and has messages.
  - Its lines go through D-1, D-2 and D-4. Listings keep no trace, so they are not paired.
  - The previous error is "same" when one of its forms is a form of the test's primary class.
  - The comparison is unknown, and nothing shows, in four cases:
    - the primary class's key depends on the own frame (located templates and default
      messages, D-2), because a listing has no trace;
    - a start lacks the lines its template needs;
    - the server cut the message (4,000 characters, V-34) before the key and its identity
      holes ended;
    - no start matches, but the build had more than five distinct starts for the test, so a
      dropped one might have matched.
  - Rows show "Same error in <build>" or "Other error in <build>". The facts show "Same error in
    the previous failed build: n of k". Nothing shows without messages.
  - A test rerun inside its task gets no comparison. Its failed attempts are sub-results
    (§15.10), which a listing does not include, and the parent carries no message of its own.
    This is a known limitation.
- **Requests.** No new request.

### D-9 Bounds and determinism

- **Linear.** One pass over attempts with memoized classification. At most 2,000 patterns are
  tried on two to four whole lines, behind the literal pre-filter of D-4. Pairing is linear in
  occurrences, for a few groups.
- **Deterministic.** No clock, random number or process culture enters a key: folding is
  invariant, and folded keys compare ordinally. Output order never comes from a hash set or a
  dictionary of strings, whose order .NET randomizes for each process.
- **Sizing.** A test classifies 200 failures × 14 attempts with distinct messages. Its time goes
  in the handoff, not into an assertion.

**Profile cases:**
- A, A, B gives A, "2 of 3".
- A tie goes to the latest.
- Three generic and one specific give the specific.
- Only generic gives the most frequent generic.
- The fallback, no message, a flaky test, and paired forms counted as one class.

**Membership cases:**
- A test whose primary error is A and that also hit B has a row under A and a muted row under B.
- An error that is no test's primary error has a cluster of muted rows.
- Most common errors and Same error count every test that hit the error.
- An unlinked test in two of the clusters that Same error reads counts once.

**History cases:**
- The xUnit header with `Expected: 5` and with `Expected: 6` stay apart.
- A start without its `Expected:` line, and a message cut at 4,000 characters inside an
  identity hole, compare as unknown and show nothing.
- A primary error keyed on its own frame compares as unknown.
- With six distinct starts, five kept, an absent match is unknown, never "Other error".

**Pattern cases:**
- `*` and `?`, anchoring, folding, and with or without the type.
- A 1 MiB line generated in the test.
- Limits and duplicate names in configuration.

## Risks

| Risk | Mitigation |
| --- | --- |
| Pairing joins two causes: same test, same own frames, different text in two groups | The whole own-frame chain with line numbers, one form per group, and the facts name the test that paired, so the merge is visible. A switch to turn pairing off waits for evidence that it is needed |
| Unconfirmed French forms | They stay out of the catalog, V-40 to V-42 track them, and pairing and rules cover them meanwhile |
| Report size budget | Phase 3b re-measures it. If it is exceeded: three other errors at most, then "+n" |
| Muted rows grow By error: a test appears once for each of its errors | The 200 × 14 budget case has one error per test. Phase 3b also measures a report where every test has three errors, and records both sizes. Over budget, a muted row drops its group cells first |
| Script cap | About 150 bytes added; the cap test runs in phase 3b |
| Overview "Latest error" against By error's primary error | The Errors column and the guide explain the difference |
| Listing parse cost (phase 4a) | Only failed results carry messages, and a record keeps only the start of its message; measured with `Measure-TestFailurePipeline.ps1` |
| A bad rule fails every cmdlet that loads the configuration | Same as every key today; its message names the rule (D-7), and phase 1 documents it |

Deviations from the design, with their reasons:

- **Files of phase 2.** The templates are matched in code, in `ErrorTemplates.cs`, which returns
  a `TemplateMatch`; there is no `ErrorTemplate.cs`. Folding, lines, signatures, forms,
  occurrences, pairings and profile entries each have a file of their own in the `Errors/`
  folder under `src/AdoToolkit.Core/Reporting/`.
- **Phase 2 tests** were written beside the code rather than before it. They cover the test
  matrix as planned.
- **Rules read inner exceptions.** A rule is also tried on each line that starts with `--->`,
  because Selenium and `HttpClient` put the cause of a failure in an inner exception.
- **Two more built-in patterns,** both read from the packages: "Unable to connect to the remote
  server" (.NET Framework) under `ConnectionRefused`, and "Timed out waiting for driver service
  to initialize" (Selenium) under `WebDriverSession`.
- **A located template without an own frame** keys on the template and its identity text, not on
  its whole text (D-2). Two MSTest timeouts of different tests then merge, as their durations and
  test names are values.
- **Same template, same language** (D-3) refuses a pairing only for a template that has both an
  English and a French form, such as MSTest's. An English-only template, such as xUnit's, appears
  in both stages, and the application text in its identity holes is what differs.
- **Configuration errors** reuse `InvalidConfiguration`, with the JSON path of the bad value as
  its argument, such as `reporting.errorRules[2].patterns[0]`. A separate `InvalidErrorRule`
  message would have said the same.
- **Error labels** in the Errors column are the rule name, else the line with its short exception
  type, cut at 60 characters, not the short type alone (D-5): two errors of one type would read
  alike.
- **A rule names its cluster in place of the exception type** (D-6), which then stays in the
  line; the heading keeps one item on the type's row.
- **"Every failed attempt"** replaces "{n} of {n} failed attempts", which read badly for one
  attempt in both languages. The key `TestReportEveryFailedAttempt` was added in phase 3b.
- **The facts row also shows for one test whose error has several forms,** so that the pairing
  that joined them is explained. The Generic count of the summary line shows only when it is not
  zero.
- **Most common errors** orders by all the tests that had the error, then by display order. Same
  error, not linked, breaks a tie between clusters by display order.
- **The `bilingual` fixture** leaves out A13, which needs a third group; the classifier tests
  cover it.
- **Across builds, a start keeps the pipeline key of its first result,** and "Other error" needs
  evidence: a start that was not cut, from a stage or job where the test had its primary error in
  this build. Otherwise a French failure of the previous build would read as another error when
  this build failed in English only. This adds a fifth case of "nothing shows" to D-8. A start
  also stops at 8,192 characters.
- **The comparison is computed by the classifier,** with the report's rules, and the model
  carries it; the renderer reads no rule.
