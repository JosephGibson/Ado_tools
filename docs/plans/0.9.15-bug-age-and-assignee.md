# 0.9.15 plan: how old a bug is and who has it

One user-visible feature: the failed-test report answers the first question of triage —
has someone already filed this bug for this run, and is anyone on it?

`AdoTestBug` gains `CreatedDate` and `AssignedTo`, read in the bug lookup that already runs.
A bug created at or after the build's queue time is marked **New** on its chip, wherever a bug
chip appears. The bug's one-line summary — in the Open bugs heading and in the Details card —
names the assignee, says plainly when a bug is unassigned, and gives the creation date; the Open
bugs summary line counts the bugs opened after the build was queued.

This is the item the developer deferred in the last pass of 0.8.5: "Bugs opened in this run,
tagged New in lighter red", section 9 and the "New open bugs" row of the last-pass decisions of
[the 0.8.5 plan](../archive/plans/0.8.5-report-styling.md).

## 1. Outcome

A person opening the report on a failed build can tell, without leaving it:

- which open bugs were filed after this build was queued, from the chip alone, in every view;
- who owns each open bug, or that nobody does;
- when each bug was filed, so a wrongly marked **New** corrects itself on sight;
- how many of the report's bugs were filed after the build was queued;
- which bugs an owner has, by typing that owner's name in the report's search.

`Get-AdoBuildTestFailure` output gains two properties. No new request, no new parameter, no
change to an existing property, no change to the default console tables.

## 3. Decisions

| Question | Choice | Why |
| --- | --- | --- |
| The **New** threshold | The build's **queue time** (`model.Build.QueueTime`) | It is one value, a property of the build, and it cannot move: the first run's start depends on which runs were retrieved and on rerun and stage ordering, so two reports of the same build could disagree. It is present even when no run carries a `startedDate`. It errs wide, not narrow — a bug filed while the build waited in a queue is marked **New** — and a false **New** is the cheaper error: the marker says "this may have been filed for this run", and the creation date beside it settles the matter. Missing a bug that *was* filed for the run is the costly miss |
| An upper bound on the window | **None.** The wording says what the data supports: *opened after this build was queued*, never "in this build" | The bug read has no `asOf`, so it reads work items as they are now. Regenerating an old build's report would mark a bug filed last week for a later build, and no upper bound is available: the run history holds the current build and earlier ones only, and `GeneratedAt` is always later than any bug. Reading the next build of the definition would buy a true bound for one more request on every report, to fix a case that arises only when an old report is regenerated — not worth it for an additive feature. So the claim is narrowed to a true one instead, the date is always beside it, and the guide says the marker is about the queue time, not about the build's lifetime |
| Which bugs carry the new facts | Only a bug with `IsOpen == true`: the marker, the date, the assignee and **Unassigned** all require it | `IsOpen` is null for a bug that never came back **and** for one that came back without a `System.State` — the second has a creation date, so a rule keyed on the date alone would print **New** on a grey **Not read** chip. One rule — these facts belong to a bug that was read whole — keeps the grey chip meaning exactly "unknown", gives the Open bugs line no contradictory pairing such as a date beside **Not read**, and is one condition to test. It is the same stance the report already takes: an unreadable bug is grey and its test counts as *without* an open bug |
| A read, open bug with no creation date | No marker, and no date on its line | **New** is a claim about a date. Without the date there is no claim. The absence of a marker means "not known to be new", not "old" |
| A build with no queue time | No bug is marked, and the summary omits the count | No threshold, no claim. The dates still show |
| The exact treatment of **New** | The bug chip itself carries it: `✦` before `#id`, in a lighter red (`--fail-new`), with a title and screen-reader text saying it was opened after the build was queued. The word **New** appears, as a text chip, only on the bug's summary line | Red because red means bug in this report, lighter red because the filled violet chip is the test's **New** and must stay unique — the developer asked for a lighter red. `✦` is the glyph the report already uses for new, so the meaning carries while the colour says *what* is new; colour never carries meaning alone. Marking the chip, not adding a chip beside it, is what keeps it "wherever bug chips appear": `BugChip` is one method, so the Overview's narrow **Open bugs** column, the By error facts line, the Details card and the attempt's Associated bugs all get it with no drift. A word in that column would widen it by about 3.5 rem and undo part of the 0.8.5 density pass |
| Where the date and the assignee are rendered | In `BugText`, the bug's one-line summary, which the Open bugs heading **and** the Details card list both call | The ask is for the Open bugs heading, and `BugText` is that line. Putting it there also gets the card, which is what makes an owner searchable: search matches the text of a `.failure-card` and then shows or hides the table rows and bug groups by their card's verdict, so a name only in the Open bugs heading would match nothing. One call site, both places, and search works. The order on the line becomes title, state, date, assignee, with the bug's type and project after them in the Open bugs heading as today; moving those two into `BugText` as well would change the card and is left alone |
| An Overview card counting bugs filed for this run | **No.** The Open bugs view gets a summary line instead: `Open bugs: N · Opened after this build was queued: K` | The cards row already holds up to four panels side by side, and each answers *what kind of build is this*. A bug-filing count answers a question about the bug list, and a fifth panel for one integer is what crowds that row at 1280 px. The Open bugs tab already shows the bug count, and the summary line sits at the top of the view that holds the dates and the assignees, one key away. The precedent is By error's own summary line. If the developer wants it on the Overview, it is a four-line addition to `Glance` and the plan can take it at approval |
| The two new properties in the format file's default views | **No change** | `AdoTestBug`'s default table is already five columns, and `Title` — the column that identifies a bug — takes whatever width is left. An identity renders as `Name <unique.name>` and a date-time is about 20 characters; adding both would leave `Title` roughly 30. Both values are one `Select-Object` away, the help's `OUTPUTS` lists them, and the guides show the explicit `Format-Table`. Keeping the table also keeps the Pester pin on its row honest. The alternative — `AssignedTo` alone, at `Title`'s expense — is the developer's call at approval |
| Where the identity is parsed | A new internal helper for the bug read, with a rule that never loses a name. `TestCaseDetailService` is **not** changed | Sharing its stricter rule is what produces a false **Unassigned**: it returns null for an identity object without a usable `displayName`, and the report would then tell a triager that an owned bug has nobody on it. Loosening that rule in place would change `Export-AdoTestCase -IncludeDetail` output, which is not this feature. Two rules, where the bug read's is a superset, can disagree only by showing a name the Test Case detail omits — cosmetic, not a false claim |

## 4. Design

### 4.1 The two properties

```csharp
// The day the bug was filed, as the server records it, in UTC; null when it could not be read.
public DateTimeOffset? CreatedDate { get; init; }
// Who the bug is assigned to; null when nobody is, or when it could not be read.
public AdoIdentityRef? AssignedTo { get; init; }
```

Both additive, both null for a bug that could not be read. `AssignedTo` is also null for a bug
that is read and unassigned; the report tells the two apart by `IsOpen`, which is true only for
a bug read whole, exactly as it already does before trusting `State`.

### 4.2 The read

`Fields` in `TestBugResolver` becomes seven entries, `System.CreatedDate` and `System.AssignedTo`
appended. `BugData` gains the two values; `Compose` sets them. A new internal
`WorkItemFieldValues` holds `Date` and `Identity` over a field bag:

- `Date` — a `JsonElement` string parsed with `GetDateTimeOffset().ToUniversalTime()`, as
  `FieldValueMapper` does; anything else, or a parse failure, is null. No diagnostic: a missing
  optional field is not a lookup problem, and the report simply makes no claim.
- `Identity` — never loses a name that the payload holds:
  - absent, JSON null, or an empty or blank string → null, which the report reads as unassigned;
  - a non-empty string → that text as `DisplayName`, the Server 2020 `DOMAIN\user` shape;
  - an object → `DisplayName` from the first non-empty of `displayName`, `uniqueName`, `id`,
    with `Id` and `UniqueName` set from their own properties when present;
  - an object holding none of those three → null. It names nobody that could be shown, and
    there is nothing to print either way.

Both are bounded reads of one field; neither can throw out of the resolver.

### 4.3 The chip

```csharp
private bool IsNewBug(AdoTestBug bug) => bug.IsOpen == true
    && model.Build.QueueTime is { } queued && bug.CreatedDate is { } created && created >= queued;
```

Both sides of the comparison are `DateTimeOffset`, so it compares absolute instants and no
offset or daylight-saving rule enters it. `IsOpen == true` is what keeps the marker off a grey
chip whose bug came back without a state.

In `BugChip`, a bug that `IsNewBug` adds `bug-new` to the chip's class, prepends
`<span aria-hidden="true">✦</span>`, and extends the title and the screen-reader text with
**Opened after this build was queued**.

### 4.4 The bug's summary line

`BugText` — the Open bugs heading line and the Details card's open-bug list — gains, for a bug
with `IsOpen == true` only, after the title and state:

- `Created on: 2026-10-02` when the date is known, in the report's offset, the day only, as the
  run history already formats a day;
- the **New** text chip, when `IsNewBug`;
- `Assigned To: Nadia Roy` from `AssignedTo.DisplayName`, or **Unassigned**.

A bug with `IsOpen` null keeps today's line exactly: title, then **Not read**. The two cases are
mutually exclusive, so no line can pair a date with **Not read**.

The Open bugs view gains a summary line above its table, as By error has one:
`Open bugs: N · Opened after this build was queued: K`, the second part left out when the build
has no queue time.

### 4.5 The colour

A new token `--fail-new`, lighter than `--fail` on screen and darker in print, defined in both
palettes of `src/AdoToolkit.Core/Reporting/Assets/test-failures.css` and added to the `colours`
array of `ThemeContrastTests`, which requires 4.5:1 on `--bg`, `--surface`, `--surface-2` and
`--code-bg` in both. The chip keeps its border and 12 % tint; only the text and border colour
change, so its box and the column's width do not.

### Phase 5 — The live check V-37

Depends on: phase 1 for the field list. Files disjoint from phases 2, 3 and 4.

Server 2020 is not confirmed to return `System.CreatedDate` and `System.AssignedTo` in a
`WorkItemsBatch` field projection, and the identity's shape there — an object or
`Display Name <DOMAIN\user>` — is not observed. The code handles both shapes; the plan does not
guess which, and owes the question to **V-37**.

The script's existing batch request reads a Test Case with relations and no field projection, and
the bug lookup runs inside the cmdlet where the raw response is not visible, so V-37 **sends its
own** projected request: the bug IDs that the V-30 block already collected from the retrieved
set, with the seven-field list and `errorPolicy: omit`.

| File | Change |
| --- | --- |
| `tests/Live/TestFailures.Live.ps1` | `V-37` in `$items`; its own projected bug request and verdict block |
| `tests/Live/Live.Common.ps1` | Pure helpers: the field-presence count and the identity-shape classifier |
| `tools/tests/LiveAudit.Tests.ps1` | Synthetic cases for both helpers and for the block's validation |
| `docs/tooling.md` | The row for the script, its new optional input, and the V-37 IDs |

What it compares, printing structure only — no names, no dates, no identities:

- per returned bug, whether `System.CreatedDate` and `System.AssignedTo` are present;
- each present `System.AssignedTo` classified `IDENTITY_OBJECT`, `STRING` or `OTHER`;
- the module's own counts for the same IDs: how many carry a non-null `CreatedDate` and a
  non-null `AssignedTo`.

Omission cannot be told from "nobody is assigned" without a bug known to be assigned, so the
check takes an optional `ADOTOOLKIT_LIVE_ASSIGNED_BUG_ID` — a bug the developer knows has an
assignee — and reads it in the same request.

| Verdict | When |
| --- | --- |
| `PASS V-37 BUG_FIELDS_PRESENT_AND_SHAPED` | Every returned bug carries `System.CreatedDate`; every present `System.AssignedTo` is `IDENTITY_OBJECT` or `STRING`; the module's counts equal the raw counts; and the assignee half is settled — the named assigned bug came back with the field, or at least one bug did |
| `FAIL V-37 CREATED_DATE_ABSENT` | A returned bug has no `System.CreatedDate` |
| `FAIL V-37 ASSIGNED_TO_SHAPE_UNKNOWN=<n>` | A present `System.AssignedTo` is `OTHER` |
| `FAIL V-37 ASSIGNED_TO_OMITTED` | `ADOTOOLKIT_LIVE_ASSIGNED_BUG_ID` came back without the field |
| `FAIL V-37 MODULE_COUNTS_DIFFER` | The module's non-null counts differ from the raw presence counts |
| `INCONCLUSIVE V-37 NO_BUGS_ON_REPORTED_TESTS` | The build's reported tests have no bug |
| `INCONCLUSIVE V-37 NO_ASSIGNED_BUG` | No bug came back assigned and no `ADOTOOLKIT_LIVE_ASSIGNED_BUG_ID` was given |

`NOTE` lines carry the counts and the shape names before the verdict, as the V-28 probe does.
One verdict per ID. An agent never runs it.

## 8. Risks and what is owed

| Risk | Handling |
| --- | --- |
| `System.CreatedDate` or `System.AssignedTo` absent from a Server 2020 batch projection | Both properties are null-tolerant end to end: no marker, no date, no assignee, no diagnostic. Owed to V-37 (phase 5) |
| The identity comes in a shape the parser does not know | The fallback chain of section 4.2 takes any name the payload holds; only an object with no `displayName`, `uniqueName` or `id` gives null, and it holds no name to print. V-37 fails on an `OTHER` shape, which is the evidence to fix it |
| A long queue wait marks an unrelated bug **New** | Accepted, with the date beside the marker. Section 3 records the reason |
| An old build's report regenerated today marks a bug filed for a later build | The wording claims only what the data supports — *opened after this build was queued* — and the guide says so. Section 3 records why no upper bound is taken |
| `--fail-new` fails the 4.5:1 check on a surface | The token is chosen against `ThemeContrastTests` before the markup is written; the test is phase 2's first failing test |
| Goldens churn beyond the intended change | `update-goldens`, reviewed in both cultures; the fixture change is deliberate — its builds have no `QueueTime` today, so without it no golden would show the feature at all |

Not in scope: closed bugs, a bug's history, the Overview card (section 3), the default console
tables (section 3), `TestCaseDetailService`'s own identity rule (section 3), and any change to
`docs/schemas/testcase.v1.schema.json`, which the failed-test report does not use.

## Critique

Critic: `gpt-6.1-sol` through the `critique` skill, effort xhigh, repository mode, 2026-10-04.
Five findings, each verified against the tree before triage.

1. **Adding assignees to bug headings will not make them searchable** (HIGH) — **applied**.
   Verified: `apply` in `src/AdoToolkit.Core/Reporting/Assets/test-failures.js` matches
   `.failure-card` text and then hides rows and bug groups by their card's verdict, so a name
   only in the Open bugs heading would match nothing. The plan's "for free" claim was wrong.
   The date and the assignee now render in `BugText`, which the Details card's bug list calls as
   well as the Open bugs heading, so the name is inside the card that search reads. Phase 2
   test 7 pins it, and section 1 keeps the search promise because it is now true.
2. **V-37 cannot inspect the projected bug batch the plan says already exists** (MEDIUM) —
   **applied**. Verified: the script's own batch request expands relations on a Test Case with no
   field projection, and the bug lookup runs inside `Get-AdoBuildTestFailure`, whose raw response
   the script never sees. Phase 5 now sends its own projected request for the bug IDs the V-30
   block collected. The "field absent from a bug that has one" verdict was likewise not
   implementable: an optional `ADOTOOLKIT_LIVE_ASSIGNED_BUG_ID` supplies a bug known to be
   assigned, and without it the assignee half is `INCONCLUSIVE`, not a pass.
3. **An unreadable assignment becomes a false Unassigned claim** (MEDIUM) — **applied**.
   Verified: `TestCaseDetailService.Identity` returns null for an object without a usable
   `displayName`, and the plan rendered null as **Unassigned** for any read bug. The identity
   rule now falls back to `uniqueName` and then `id`, so any payload holding a name yields one,
   and the only null-from-present case holds no name at all. The decision to share the parser
   with `TestCaseDetailService` is reversed: loosening it in place would change
   `Export-AdoTestCase -IncludeDetail`, which is not this feature. Phase 1 test 3 covers every
   shape.
4. **A grey chip can satisfy the proposed New predicate** (MEDIUM) — **applied**. Verified:
   `IsOpen` is null whenever `System.State` is missing, including for an item that came back, so
   a returned bug with a creation date and no state would have taken the marker on a grey chip.
   `IsNewBug` now requires `IsOpen == true`, and the same condition gates the date, the assignee
   and **Unassigned**, which also stops a line pairing a date with **Not read**. Phase 2 test 3
   is that case.
5. **The New rule has no boundary for bugs created after the build** (MEDIUM) — **applied**.
   Verified: the bug read has no `asOf`, and `RunHistoryService.ReadEarlierAsync` reads the
   current build and earlier ones only, so no later build is available as a bound. Rather than
   buy a true bound with one more request on every report, the claim is narrowed to what the
   predicate tests — *opened after this build was queued* — in the strings, section 1, and the
   guide, which states the regenerated-report case. Section 3 records the rejected alternative.
